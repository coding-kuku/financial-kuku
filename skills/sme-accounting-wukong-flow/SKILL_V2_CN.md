# SME Accounting Wukong Flow V2 中文版

## 概述

使用本技能将原始会计证据转换为受控的记账动作。
执行硬性会计阀门：如果证据不足、置信度过低、风险过高，或余额差异无法解释，则停止过账并转入异常处理。

## 核心原则

- 不对不确定交易过账
- 无证据不判断
- 有风险必须标记风险
- 保持每一个判断可追溯
- 要求业务链条在逻辑上闭合

## 输入要求

### 1. 必需输入类型

对于任何记账任务，至少要求提供：

- 银行流水数据
- 每一笔交易对应的发票材料，包括销售发票、采购发票，或其他能够与流水对应的票据证据

在适用场景下，另外要求：

- 当流水中涉及工资相关交易，且现有证据无法清晰判断性质时，需要一并提供工资数据
- 当流水中涉及社保相关交易，且现有证据无法清晰判断性质时，需要一并提供社保数据
- 对于任何现有证据仍无法清晰判断业务性质的流水，需要一并提供其他相关支持材料

### 2. 可接受的输入类型

可接受的输入包括：

- 银行流水
- 银行回单
- 采购发票
- 销售发票
- 工资数据
- 社保数据
- 固定资产清单
- 存货或出入库记录
- 总账汇总或历史账面余额
- 用户陈述或用户确认的业务事实

### 3. 输入提交要求

每个任务还应明确提供：

- 主体名称
- 目标期间或日期范围
- 足以将每一个判断回溯到原始证据的来源追踪信息

当需要在悟空系统中执行实际记账动作时，还应提供：

- 正确的账套

### 4. 最低必填字段

每条记录至少标准化为以下字段：

- 日期
- 金额
- 对手方
- 摘要
- 来源

当处理原始银行对账单数据时，还必须保留可回溯到原始文件、工作表和行号的完整来源追踪信息。

### 5. 输入充分性

不要仅仅因为交易类别就直接挂起。
应根据是否已具备足以支持防御性会计处理的最小必要信息来决定。

最小充分事实必须同时支持以下几点：

- 资金方向清晰
- 期间归属可用
- 业务性质可识别
- 对手方角色可识别
- 科目路径可合理确定
- 能在输出中明确说明风险

如果最小充分事实已经具备，则过账。
如果最小充分事实尚不具备，则挂起。
如果一个批次中同时包含清晰与不清晰的交易，则先过账清晰部分，只挂起不清晰部分。

避免两类错误：

- 对不确定流水过度过账
- 对已经可判断的流水过度挂起

### 6. 缺失输入处理

当一笔交易无法过账时，只询问使其可过账所需的最小补充信息。
不要在并非必要时索取大而全的资料包。
使用能够解决会计判断的最小事实集合。

按交易类型划分的典型最小缺失信息：

- 工资：
  - 员工身份
  - 工资所属月份
  - 银行金额是否为实发净额
  - 是否已计提工资
- 社保：
  - 申报所属月份
  - 单位承担部分
  - 个人承担部分
  - 是否包含公积金或个税
- 自然人对手方：
  - 人员身份
  - 与公司的关系
  - 付款业务性质
  - 是否代表某个单位收付
- 性质不明的流入：
  - 是收入、退款、往来回款还是股东款
  - 是否有关联客户或供应商
  - 如果主张为收入，是否已经履约或交付
- 退款或退回流水：
  - 对应原始哪笔付款或交易
  - 原始性质是采购、费用、押金还是往来款

### 7. 用户确认事实

如果用户已经提供了足够具体的业务事实，且足以在可接受风险下确定处理方式，则不强制要求正式单据。

当用户的明确确认清楚说明以下事项时，可将其视为可用证据：

- 对手方是谁
- 款项用途是什么
- 属于哪个期间
- 属于收入、费用、工资、社保、退款、往来款还是股东款
- 过账所需的关键拆分信息，例如单位承担与个人承担的划分

当依赖用户确认事实时：

- 记录该处理依据来自用户确认
- 保持该交易可追溯到银行流水行
- 如果用户表述在实质上仍有歧义，则继续挂起

不要使用一刀切规则，例如：

- 所有工资都必须挂起
- 所有社保都必须挂起
- 所有自然人流水都必须挂起
- 所有性质不明的流入都必须挂起

当用户提供的事实已经充分时，这些类别也可以过账。

## 工作流

严格按以下顺序执行，不得跳步。
当前步骤未通过校验前，不得进入下一步。

对于每个任务，工作结构保持为：

- Input
- Process
- Output
- Action Guide
- Constraints

### 第 1 步：任务确认

在任何记账工作开始前，先确认：

- 主体名称
- 目标期间或日期范围
- 本次任务是基于原始证据重建账务，还是复现既有账
- 当前任务已有的来源材料
- 是否具备可将每一个判断回溯到原始证据的来源追踪信息
- 如果需要在悟空中执行实时操作，是否已确认正确账套

如果必需源证据缺失、来源追踪不足，或任务模式不明确，则先停止并补齐说明或材料，再继续后续步骤。

### 第 2 步：环境初始化与入账前准备

在任何过账之前，核验：

- 各主体物理隔离
- 一级科目使用中国企业会计准则标准科目
- 费用明细科目要细化，不使用笼统的“其他”费用口径
- 对手方已绑定到应收、应付及其他往来科目
- 银行科目按真实银行账户拆分

如果科目表或辅助核算设置不完整，则停止工作。

### 第 3 步：数据接收与预处理

接收源数据并将每条记录标准化。

如果付款方或收款方是支付宝、微信、备付金等中间账户，不得将其视为最终对手方。
应读取备注或回单明细，恢复真实业务对手方。

### 第 4 步：银行流水二次标准化

当用户只提供原始银行流水数据时，不得直接从原始文件判断业务性质或直接过账。
必须先使用以下模板对原始银行流水行进行标准化：

- `normalization_deal/bank_flow_secondary_normalization_template.md`

该文件是过账判断、凭证准备和系统过账之前的强制中间标准。

最低要求：

- 在 `01_raw_import` 中保留原始银行流水行
- 将每一条有效银行流水标准化到 `02_normalized_txn`
- 将每一条标准化后的流水放入 `03_decision_queue` 中且只能处于一个决策状态
- 只允许以下决策状态：
  - `post`
  - `hold`
  - `escalate`
- 只有可直接过账的流水才进入 `04_post_ready`
- 保持标准化流水到原始文件、工作表、行号的完整来源追踪
- 对每一条挂起流水，必须写明：
  - 挂起原因
  - 最小缺失信息

不得直接从原始银行流水表过账。
在标准化结构完成前，不得继续到凭证生成。

### 第 5 步：来源冲突处理

当总账汇总、银行流水、发票、工资表、社保表或用户陈述相互冲突时，不得静默混合为一个过账结果。

按以下顺序处理冲突：

1. 原始源证据
2. 用户确认事实
3. 历史账面余额
4. 派生汇总或既有汇总结果

必须执行的动作：

- 识别具体冲突字段
- 说明当前判断所采用的权威来源
- 分开处理：
  - 可过账项
  - 挂起项
  - 争议项
- 在争议项未解决前，不得关账

如果任务目标是复现既有账，而不是基于原始证据重建账务，则在沿用旧账处理前必须明确说明该模式。

### 第 6 步：业务识别

先判断每一笔交易的一级业务性质。
以下分类作为常见一级分类使用，并在需要时继续细分。
如果交易实质需要拆分处理、增加二级标签，或暂时保留待确认状态，不得强行塞入单一固定标签。

常见一级分类包括：

- 销售及客户收款
- 采购及供应商付款
- 费用付款
- 工资及员工相关付款
- 税费及社保相关付款
- 往来款项变动
- 股东或融资相关资金
- 资产类支出
- 退款、冲回及退回
- 自有账户之间划转或转入中间资金账户
- 不确定

对每个分类结果输出：

- primary classification
- secondary tag when needed
- confidence score
- evidence basis

如果置信度低于可用阈值，则不得生成凭证。
该交易应转入异常处理。

### 第 7 步：对手方归一化

在使用或创建辅助核算前，先对名称进行归一：

- 按相似度匹配历史名称
- 根据交易行为和频次推断性质
- 在业务性质未明确前，不得批量创建新对手方

### 第 8 步：会计期间归属

采用权责发生制：

- 收入按履约或业务完成确认
- 成本与相关收入匹配
- 费用在实际发生期间确认
- 发票是证据，不是唯一记账依据

如果银行日期与业务日期不一致，优先采用业务日期。
对跨期事项进行标记，并提出调整分录建议。

### 第 9 步：会计处理方案比较

对每笔交易生成多个处理方案并打分。
按以下优先顺序判断：

1. 发票或正式证据
2. 历史交易模式
3. 对手方性质
4. 摘要文本

选择质量最高且合理的处理方案。
如果没有足够合理的方案，则不得过账。

### 第 10 步：金额合理性与风险控制

检查以下异常情况：

- 单笔金额远高于历史水平
- 费用收入比异常
- 收入或成本突然大幅波动
- 持续异常亏损或异常盈利

一旦触发：

- 标记风险等级
- 降低自动化优先级
- 在关账前要求给出解释

### 第 11 步：凭证生成

要求：

- 借贷必须严格平衡
- 摘要必须反映业务实质
- 处理方式必须符合风险隔离规则

执行以下硬规则：

- 股东资金在无出资证明时 -> 记入其他应付款
- 无发票收入 -> 仅可在显式风险标记下允许
- 非经营性个人支出 -> 记入其他应收款-个人

### 第 12 步：异常处理与批次分流

将异常分为：

- 低风险：允许自动处理
- 中风险：需要确认
- 高风险：禁止自动处理

对每个异常输出：

- recommended treatment
- alternative treatment
- risk explanation

一个批次只有在每一条源交易都明确落入以下之一时，才算处理完成：

- posted
- held with explicit reason and minimum missing information
- escalated with explicit risk reason

不得让任何交易处于隐含或静默状态。

### 第 13 步：期末处理

期末执行：

- 损益结转
- 工资计提
- 折旧计提
- 所得税估计

同时校验业务链条一致性：

- 销售应有成本结转或存货减少
- 采购应进入存货或费用
- 工资应与员工或社保证据对应

如果链条断裂，则标记异常并禁止关账。

### 第 14 步：银行对账

使用公式：

`bank balance = book balance + reconciliation items`

可能的调节项：

- 未达账项
- 在途资金
- 第三方平台余额

将银行余额视为强校验锚点，但不视为绝对真相。
每一项差异都必须可解释。
如果无法解释，则不得关账。

### 第 15 步：报表、税务映射与关账

在出报表或关账前，核验：

- 资产负债表平衡
- 利润逻辑一致
- 跨期事项已有调整建议
- 报税基础数据已生成但仍可复核

关账后：

- 不得直接修改
- 使用红字冲回方式
- 重新录入正确凭证
- 重新执行全部校验

### 第 16 步：会计复核报告

在关账前，先依据标准 md 模板生成面向会计的 markdown 复核报告，再基于该 md 报告生成 docx 报告。

执行顺序：

1. 生成 markdown 报告
2. 基于 markdown 报告生成 docx 报告

md 模板路径必须使用 `Deliverables and Output` 中定义的路径。
不得为 docx 单独维护另一套内容模板。

## 决策规则

### 1. 通用决策规则

#### 资金方向优先规则

在相信摘要文本之前，始终先判断资金方向。

- 如果银行流水是流入，优先考虑：
  - 客户回款
  - 往来款回流
  - 保证金或押金退回
  - 退款
- 如果银行流水是流出，优先考虑：
  - 采购付款
  - 费用付款
  - 工资、税费或社保
  - 转入中间资金账户

不能仅凭“采购”“货款”“用品”等关键词推翻资金方向。

特殊处理：

- 带有采购类文本的流入，仍可能是对方因向本公司采购而支付的客户款
- 带有销售类文本的流出，仍可能是退款、佣金或往来款变动

#### 证据分层规则

将证据分为三层，并据此决定自动化范围。

Layer A - 直接证据：

- 发票
- 回单或汇款通知
- 工资或社保清单
- 订单号
- 出入库记录
- 已知供应商或客户映射

Layer B - 半直接证据：

- 稳定的历史对手方模式
- 从支付宝、微信或银行备注中提取出的商户名称
- 已在历史上确认过的同类处理方式

Layer C - 弱证据：

- 只有原始摘要文本
- 只有中间账户名称
- 未映射的自然人对手方
- “货款”“用品”“消费”等泛化表述

判定阈值：

- A 层且与资金方向一致 -> 允许自动过账
- 只有 B 层 -> 可以给出建议，通常挂起，除非模式稳定且低风险
- 只有 C 层 -> 不得自动过账

#### 置信度升降因素

以下情况提升置信度：

- 方向、商户、用途和历史模式全部一致
- 存在供应商或客户映射
- 存在订单号或出入库引用
- 同样处理方式已在前几个月确认

以下情况降低置信度：

- 中间账户未穿透
- 自然人未完成映射
- 方向与摘要冲突
- 摘要过于笼统
- 无支持性单据
- 金额表现出类似资产购置特征但受益期不明

#### 最低充分过账规则

不要仅因类别而挂起交易。
应根据是否已经具备足以支持防御性会计处理的最小必要信息来决定。

如果最小充分事实已经具备，则过账。
如果最小充分事实尚不具备，则挂起。
如果一个批次中同时包含清晰与不清晰的交易，则先过账清晰部分，只挂起不清晰部分。

最小充分事实必须同时支持以下几点：

- 资金方向清晰
- 期间归属可用
- 业务性质可识别
- 对手方角色可识别
- 科目路径可合理确定
- 能在输出中明确说明风险

避免两类错误：

- 对不确定流水过度过账
- 对已经可判断的流水过度挂起

### 2. 对手方与穿透规则

#### 中间账户穿透规则

绝不能将中间账户视为最终对手方。

适用名称包括：

- 支付宝（中国）网络技术有限公司客户备付金
- 微信支付
- 待报解预算收入
- 备付金
- 平台结算或清算账户

必须执行的动作：

1. 从备注中解析真实商户或业务线索
2. 判断该流水属于：
  - 转入中间资金账户
  - 最终商户消费
  - 税费或社保代扣
  - 无法识别的平台清算
3. 同时保存：
  - 通道对手方
  - 穿透后的真实对手方

如果无法恢复真实对手方，则挂起该交易。

#### 支付宝与微信两步判断规则

对于与支付宝或微信有关的流水，分两步判断。

第 1 步：先判断这是资金划转还是最终消费。

- 如果备注表明是充值、备付、钱包，或只是泛化商户占位名称，优先处理为：
  - Dr Other Monetary Funds
  - Cr Bank Deposits
- 如果备注能够识别明确商户或订单，则进入第 2 步

第 2 步：判断业务性质。

- 采购货物 -> 应付账款、存货或预付款路径
- 办公用品、工具或低值易耗 -> 费用路径
- 类固定资产或装修类支出 -> 长期资产或待摊费用复核
- 仍不清楚 -> 挂起

在商户和用途都不充分明确前，不得直接将支付宝或微信流水计入费用。

#### 自然人对手方映射规则

如果银行对手方是自然人，不得直接假定该自然人就是最终供应商或客户。

按以下顺序检查：

1. 既有“自然人-单位”映射表
2. 同日订单或采购记录
3. 历史已确认凭证映射
4. 备注、订单号或平台记录

分类处理：

- 已映射到真实供应商或客户 -> 使用映射后的实体作为会计科目和辅助核算对象
- 多次出现但仍未映射 -> 中高风险，挂起
- 一次性且未映射的自然人 -> 高风险，挂起

除非业务证据充分，不得基于自然人自动创建新的供应商或客户。

### 3. 交易专项处理规则

#### 采购付款决策规则

对于摘要标记为“货款”或同类表述的流出流水，在三条路径中选择。

Path A - 清偿应付账款

适用于货物已收、或应付依据已经存在时。

- Dr Accounts Payable
- Cr Bank Deposits

Path B - 预付款

适用于付款发生在收货、收票或入库证据之前。

- Dr Prepayments
- Cr Bank Deposits

Path C - 挂起

适用于供应商身份、用途或与存货的关系不清楚时。

附加要求：

- 如果后续出现入库证据，则在期末或同期间生成转换分录：
  - Dr Inventory or Expense
  - Cr Accounts Payable or Prepayments

#### 流入采购词规则

如果一笔流入银行流水带有“采购服装”之类的采购性文字：

- 不得自动将其分类为采购
- 应判断是否表示对方向本公司采购而付款
- 如果本公司是销售方，则优先处理为：
  - Dr Bank Deposits
  - Cr Accounts Receivable 或收入相关路径，视证据阶段而定
- 如果确实是供应商退款或往来回款，则需要支持性证据

流入的资金方向优先于采购类措辞。

#### 社保拆分规则

对于社保扣款，默认不得一笔统记为单一费用。

要求的输入：

- 社保申报明细
- 单位承担与个人承担拆分
- 期间归属

优先处理方式：

- 单位承担部分 -> Dr 工资相关成本、费用或应付工资类路径
- 代个人支付部分 -> Dr Other Receivables 或工资清算路径
- Cr Bank Deposits

如果缺少拆分明细：

- 只有在政策允许且可追溯性保留的情况下，才允许挂起或暂记入过渡清算科目

#### 存货链条补全规则

当支持性记录能够显示货物与数量时，应补全业务链条。

仅有银行付款并不代表链条已经完成。
在确认收货后：

- Dr Inventory
- Cr Accounts Payable or Prepayments

如果缺少数量、SKU 或入库依据，则不得自动生成存货分录。

### 4. 凭证与过账控制规则

#### 同日合并规则

只有在以下条件全部满足时，才允许将多条银行流水合并为一张凭证：

- 同一天
- 同一经济实质
- 穿透或映射后的最终对手方相同
- 会计处理方式相同
- 凭证能够明确追溯到全部源流水

典型可合并情形：

- 同一供应商在同一天分多笔付款
- 同一商户被拆分为多笔小额扣款
- 同一平台商户被拆分为多笔支付

在凭证摘要或附件说明中记录所有源银行流水行 ID。

#### 凭证生成规则

要求：

- 借贷必须严格平衡
- 摘要必须反映业务实质
- 处理方式必须符合风险隔离规则

执行以下硬规则：

- 股东资金在无出资证明时 -> 记入其他应付款
- 无发票收入 -> 仅可在显式风险标记下允许
- 非经营性个人支出 -> 记入其他应收款-个人

### 5. 挂起与升级规则

#### 每笔决策的输出要求

对于每笔交易，输出：

- posting decision: post, hold, or escalate
- final classification
- confidence score
- evidence layer used
- whether counterparty was penetrated or mapped
- chosen treatment
- rejected alternatives
- voucher lines or proposed voucher lines
- source-row traceability
- risk level and reason
- reconciliation impact
- next required action
- reason if held

#### 最小缺失信息规则

当一笔交易无法过账时，只询问使其可过账所需的最小补充信息。
不要在并非必要时索取大而全的资料包。
使用能够解决会计判断的最小事实集合。

按交易类型划分的典型最小缺失信息：

- 工资：
  - 员工身份
  - 工资所属月份
  - 银行金额是否为实发净额
  - 是否已计提工资
- 社保：
  - 申报所属月份
  - 单位承担部分
  - 个人承担部分
  - 是否包含公积金或个税
- 自然人对手方：
  - 人员身份
  - 与公司的关系
  - 付款业务性质
  - 是否代表某个单位收付
- 性质不明的流入：
  - 是收入、退款、往来回款还是股东款
  - 是否有关联客户或供应商
  - 如果主张为收入，是否已经履约或交付
- 退款或退回流水：
  - 对应原始哪笔付款或交易
  - 原始性质是采购、费用、押金还是往来款

#### 挂起项输出规则

对于每一条挂起交易，必须输出：

- 挂起原因
- 最小缺失信息
- 如果补齐缺失信息即可过账
- 确认后的优先处理方式
- 在相关时给出备选处理方式
- 若未经澄清直接过账的风险

挂起项说明应短、准、可操作。
目标是帮助用户解除挂起，而不是输出泛泛的风险提示。

#### 批次完整性规则

一个批次只有在每一条源交易都明确落入以下之一时，才算处理完成：

- posted
- held with explicit reason and minimum missing information
- escalated with explicit risk reason

不得让任何交易处于隐含或静默状态。

在每个批次结束时，输出：

- 已过账交易汇总
- 已挂起交易汇总
- 已升级交易汇总
- 挂起项缺失信息清单
- 如果用户希望继续推进挂起项，下一步应做什么

#### 不清晰交易的优先响应格式

向用户报告不清晰交易时，使用以下结构：

- current decision: post, hold, or escalate
- why it cannot yet be posted
- minimum information needed
- what will be posted immediately once that information is confirmed
- what accounting treatment is expected after confirmation

示例格式：

- current decision: hold
- why: incoming cash is clear, but business nature is not
- minimum information needed: confirm whether this is customer payment, supplier refund, or shareholder transfer
- once confirmed: the transaction can be posted immediately
- expected treatment:
  - customer payment -> bank deposits against receivable or revenue path
  - supplier refund -> bank deposits against prepayments or payables
  - shareholder transfer -> bank deposits against other payables or equity-related path under policy

### 6. 来源冲突优先级规则

当总账汇总、银行流水、发票、工资表、社保表或用户陈述相互冲突时，不得静默混合为一个过账结果。

按以下顺序处理冲突：

1. 原始源证据
2. 用户确认事实
3. 历史账面余额
4. 派生汇总或既有汇总结果

必须执行的动作：

- 识别具体冲突字段
- 说明当前判断所采用的权威来源
- 分开处理：
  - 可过账项
  - 挂起项
  - 争议项
- 在争议项未解决前，不得关账

如果任务目标是复现既有账，而不是基于原始证据重建账务，则在沿用旧账处理前必须明确说明该模式。

## 交付物与输出

### 1. 标准交付物

对于每个月度记账任务，除凭证和异常判断外，还应生成以下交付物：

- machine-readable workpaper json
- posting proposal csv
- accountant review report md
- accountant review report docx generated from the md report

### 2. 命名规范

使用稳定的英文文件名，以便下游步骤直接引用。

md 模板路径：

- `normalization_deal/accounting_review_report_min_template.md`

月度期间 `YYYYMM` 的默认命名规范：

- `jietu/YYYYMM_skill_workpaper.json`
- `jietu/YYYYMM_posting_proposals_skill.csv`
- `jietu/YYYYMM_accounting_review_report.md`
- `output/doc/YYYYMM_accounting_review_report.docx`

除非用户明确要求其他命名方式，否则不得临时发明文件名。

### 3. 决策输出契约

对于每个批次或每笔交易，产出一份简洁且可审计的结果，至少包含：

- posting decision: post, hold, or escalate
- business classification
- confidence and evidence
- chosen accounting treatment and rejected alternatives
- voucher lines or proposed voucher lines
- risk level and reason
- reconciliation impact
- next required action

### 4. 挂起项输出

对于每一条挂起交易，输出：

- hold reason
- minimum missing information
- posting becomes possible if the missing information is supplied
- preferred treatment after confirmation
- alternative treatment when relevant
- risk if posted without clarification

### 5. 批次输出

在每个批次结束时，输出：

- posted transactions summary
- held transactions summary
- escalated transactions summary
- missing information checklist for held items
- next actions if the user wants the held subset posted

### 6. 会计复核报告结构

markdown 报告必须包含以下章节：

1. review conclusion
2. posting summary
3. posted item list
4. held item list
5. follow-up recommendations

最低内容要求：

- period
- entity name
- count and total amount of suggested postings
- count and reason summary of held items
- whether close is recommended
- key source conflicts, if any

md 模板路径必须使用 `Naming Convention` 中定义的路径。
不得为 docx 单独维护另一套内容模板。

## 校验清单

除非所有适用检查均通过，否则不得视为工作完成：

- 所有凭证平衡
- 银行余额差异已解释
- 应收应付余额可追溯
- 收入与成本匹配
- 费用结构合理
- 异常波动已标记
- 高风险项目未被自动过账
- 每一笔交易都处于 posted、held 或 escalated 之一
